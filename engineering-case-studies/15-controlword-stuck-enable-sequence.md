# Case 15 — Servo Controlword Stuck During CiA 402 Enable Sequence

## Context

A servo axis was integrated over EtherCAT using a CiA 402-style drive interface. Cyclic process data was available and the application attempted to bring the drive from its startup state into operation enabled before issuing motion commands.

## Symptom

The commanded controlword remained effectively at the shutdown stage and the drive did not progress through the expected CiA 402 state sequence. Motion commands therefore had no effect even though EtherCAT communication itself was active.

## Evidence

The investigation showed a characteristic split between communication and state-machine behavior:

- EtherCAT cyclic exchange was running.
- Drive status information was readable.
- The application intended to advance the enable sequence.
- The controlword observed in the process image did not advance as expected.
- The drive consequently remained below the operation-enabled state.

This evidence made a general fieldbus outage unlikely and shifted the investigation toward process-data mapping and application-side state sequencing.

## Investigation

The diagnostic path deliberately followed the command from application logic to the drive rather than changing motion parameters prematurely.

1. Confirm that the EtherCAT slave was in the expected communication state.
2. Read the drive statusword and decode the actual CiA 402 state.
3. Inspect the controlword generated by the enable logic.
4. Compare the application's controlword variable with the value actually mapped into cyclic output process data.
5. Verify that the state machine waits for the corresponding statusword transition before sending the next command.
6. Only after the drive reaches operation enabled, continue with operating-mode and motion-command diagnostics.

The expected logical progression was treated as a handshake rather than as a fixed sequence of values written without feedback:

```text
Drive status feedback
        |
        v
Select next CiA 402 transition
        |
        v
Write controlword to mapped PDO
        |
        v
Wait for matching statusword state
        |
        +--> reached -> next transition
        |
        +--> not reached -> diagnose mapping / drive condition
```

## Root Cause

The confirmed problem was in the controlword path and enable sequencing: the cyclic mapping and state-transition logic were not correctly delivering the required progression to the drive. As a result, the command remained at the shutdown stage instead of completing the CiA 402 enable sequence.

## Resolution

The process-data mapping and enable-state logic were corrected so that the application controlword was connected to the intended cyclic drive output and each transition was advanced only after validating the corresponding statusword state.

This restored a deterministic startup path from the initial CiA 402 state to operation enabled.

## Verification

The correction was verified by observing the complete command/feedback progression rather than only checking the final motion result:

- controlword changed according to the requested transition,
- statusword confirmed each resulting CiA 402 state,
- the drive reached operation enabled,
- cyclic motion commands could then be evaluated independently.

Repeated startup cycles were used to confirm that the enable sequence was deterministic rather than a one-time successful transition.

## Engineering Lessons

- EtherCAT OP does not imply that a CiA 402 drive is operation enabled; fieldbus state and drive state are separate state machines.
- A correct value inside application logic is insufficient if it is not mapped to the intended cyclic output.
- CiA 402 enabling should be implemented as a statusword-confirmed handshake, not as blind controlword writes.
- When a drive does not move, verifying `application command -> PDO mapping -> controlword -> statusword` can isolate the fault before trajectory or scaling parameters are investigated.
- Command and feedback should be observable at every layer of a motion-control architecture to make commissioning failures diagnosable.
